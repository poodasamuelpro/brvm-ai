# Étape 3 — faisabilité des sources de données réelles BRVM

**Lot 1 : recherche des sources et décision d’architecture**
**Date d’observation : 1 octobre 2026**
**Dépôt :** `poodasamuelpro/brvm-ai`
**Périmètre :** établir ce qui est réellement disponible et récupérable avant d’écrire un collecteur. Les prix et données cités ci-dessous sont des observations de pages publiques, non un jeu de données de production.

## Conclusion exécutive

Aucune API publique, documentée et libre de droits couvrant tout le marché BRVM n’a été établie par cette recherche. La voie de production la plus sûre est de demander à la BRVM les conditions, le coût et les formats de son flux de fin de séance. **SIKA Finance est la seule source où une récupération Python a été vérifiée jusqu’à une réponse JSON contenant de vraies lignes historiques**, mais le mécanisme observé est un endpoint interne, non documenté par SIKA; les droits de réutilisation et la stabilité ne sont pas établis. Il constitue un candidat de pilote interne, pas une API garantie ni une source autorisée à redistribuer.

Bloomberg, ICE, Mansa et MyStocks nécessitent un accès ou une vérification de couverture non disponible dans cette tâche. La BCEAO et les rapports des émetteurs sont de bonnes sources complémentaires pour les variables macroéconomiques et les états financiers, mais ne remplacent pas le flux de cours quotidien. **Aucun collecteur n’a été ajouté, aucune donnée n’a été insérée dans Supabase et aucune migration distante n’a été appliquée dans ce lot.**

## Raccordement à la base existante

Le schéma déjà versionné fournit les tables adaptées sans créer une base parallèle : `brvm.data_source` pour la provenance, `brvm.source_document` pour les documents et leur empreinte, `brvm.raw_ingest_record` pour le payload reçu, `brvm.market_bar` pour les OHLCV normalisés et `brvm.financial_fact` pour les faits fondamentaux. Le modèle conserve la source et le lien avec l’enregistrement brut. Les faits comptables peuvent porter la période, la publication et `available_at`; une date inconnue doit rester inconnue, sans look-ahead.

La migration place les objets dans un schéma privé `brvm` et n’accorde pas l’accès Data API à `anon`/`authenticated`. **Compatibilité du modèle vérifiée par lecture du schéma; connexion réelle à la base Supabase de l’utilisateur et insertion de données NON TESTÉES dans ce lot.** Aucun secret, fichier d’environnement ou jeton n’a été ajouté au dépôt. Aucun schéma, RLS ou bucket Storage n’a été modifié.

## Recommandation pour la prochaine tâche

1. Demander à la BRVM son offre de données EOD/historiques : contrat/licence, coût, formats, disponibilité de données passées, modalités de livraison et droits d’usage. C’est la source primaire visée pour une production fiable.
2. Pour un pilote d’analyse interne, préparer ensuite un petit collecteur SIKA **opt-in**, limité à des requêtes quotidiennes bornées, au plus trois mois par appel et à un mappage ticker explicite; conserver le payload brut, l’URL et les dates source, appliquer un backoff et les contrôles OHLCV. Garder la source marquée comme endpoint web non documenté; ne pas exposer/redistribuer les données tant que la licence n’est pas clarifiée.
3. Qualifier en parallèle ICE ou Mansa uniquement après vérification commerciale/technique concrète. Mansa nécessite une clé et une preuve d’instruments BRVM; ICE nécessite un compte et un entitlement. Ajouter ensuite les documents d’émetteurs et séries BCEAO comme connecteurs distincts.

Aucun collecteur n’est déclaré « implémenté » ou « opérationnel » par ce rapport. Le prochain lot ne doit commencer qu’après la vérification du push de ce lot, conformément à la règle **une tâche = un push = arrêt**.
